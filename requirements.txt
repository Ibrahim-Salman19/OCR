# vendor/opencv-python-stub is a local, empty package that declares itself as
# "opencv-python" version 99.99.99 and depends only on opencv-python-headless.
# rapidocr_onnxruntime (below) hard-requires plain opencv-python, which needs
# libGL -- but opencv-python and opencv-python-headless both install to the
# same cv2/ path, so having both installed means whichever installs last wins
# on disk, and it is not controllable via requirements.txt ordering (verified
# empirically: pip installs opencv-python-headless before opencv-python
# regardless of the two lines' order in this file). Since 99.99.99 outranks
# any real release, pip satisfies rapidocr's constraint with this stub
# instead of downloading the real GUI build, so opencv-python-headless ends
# up as the only actual cv2 implementation ever installed and no libGL
# system library is required at all. Verified with a real RapidOCR pass and
# the project's own preprocess_image() (cv2.cvtColor/resize/warpAffine/
# fastNlMeansDenoising) in a container with zero apt packages installed.
--find-links vendor/opencv-python-stub

# --- CRITICAL STABILITY CORE ---
# pyproject.toml's requires-python only sets a floor (>=3.10); its
# classifiers document the real, tested ceiling: 3.10-3.12 (3.13 is broken
# too -- no cp313 pandas wheel, see the classifiers' own comment). The
# python_version >= "3.14" conditional branches these packages used to carry
# here were dead weight:
# rapidocr_onnxruntime below has no cp314 build on PyPI at all (verified with
# a real `pip install` on python:3.14-slim, which fails outright on that one
# line regardless of what version of streamlit/pandas/pydantic/numpy gets
# picked), so "supporting" 3.14 in this file never actually worked. See
# docs/adr/0015 for the full incident this was discovered in -- a Streamlit
# Community Cloud deploy silently running on Python 3.14 (its dashboard's
# Python-version setting ignores this repo's runtime.txt, a known upstream
# bug: https://github.com/streamlit/streamlit/issues/15326) with a corrupted,
# partially-installed environment as a result.

# --- OCR ENGINE ---
# easyocr (PyTorch-based) is deliberately NOT installed here. It pulls in
# torch, which is ~750MB even in its CPU-only build, pushing this file's
# installed footprint to ~1.9GB against Streamlit Community Cloud's 1GB
# free-tier cap. (Note: this split was NOT the fix for the "Oh no. Error
# running app." crash seen on ocr-book.streamlit.app -- that was a separate,
# unrelated bug, a wrong entrypoint file causing ModuleNotFoundError; see the
# Dockerfile's ENTRYPOINT comment. This split is worth keeping on its own
# merits regardless.) rapidocr_onnxruntime (ONNX Runtime, no torch) is
# already this project's default and marketed engine (see the in-app FAQ: it
# replaced EasyOCR as the baseline after a bake-off showing a 7.7x latency
# improvement and 18% lower CER), so the cloud deployment loses nothing by
# not carrying the heavier legacy backend. Local dev, the Docker image, and
# CI still get easyocr via `-r requirements.txt -r requirements-easyocr.txt`
# (see that file). The UI hides the "easyocr" engine option automatically
# when the package isn't importable (blast_ocr/ui/web_app.py).
